01

项目定位与面试叙事

为什么是它 · 怎么讲

一句话定位

「让 AI 当你的 CFO」：多模态入口把记账成本降到几乎为零，AI 不只记录，还主动产出消费洞察，并用自然语言回答你关于钱的任何问题。

面试叙事：三段论

1. 为什么做（痛点）

记账产品普遍"记完就完"，坚持难、不产生价值。链路过长：记账 → 分类 → 复盘 → 决策，每一步都在流失用户——这是真实的留存问题，也是你做增长背景最有发言权的角度。

2. 怎么做（工程）

完整 AI 应用工程链路：多模态入口（语音/拍照/手输）→ LLM 结构化输出 → 规则兜底防幻觉 → 月度洞察生成 → RAG 混合检索回答账单问题。每个环节都能讲出取舍。

3. 结果（亮点）

记账成本趋近于零（说话、拍照即可）；AI 主动产出价值（月报洞察）；"一句话查账单"解决"钱去哪了"的终极追问——这是一个别人没做烂的完整闭环。

对面试 JD 的技术栈覆盖

JD 要求本项目落点讲深度的切入点
大模型应用与 Prompt 工程分类 / 解析 / 月报洞察 / 问答 4 套 Prompt 体系few-shot + JSON 结构化 + 兜底重试，防幻觉的工程手段
RAG / 检索增强账单问答彩蛋：混合检索（结构化查询 + 语义检索）为什么纯 RAG / 纯 SQL 都不够，两路合并怎么设计
多模态接入语音（微信同声传译）+ 图像（票据 OCR）识别结果不可靠时，如何用 LLM 清洗 + 人工核对闭环
后端开发与架构FastAPI + PostgreSQL + pgvector 自建全链路自建 vs 平台全家桶的取舍、降级链、成本控制
前端 / 小程序原生微信小程序 + TS + ECharts端上体验设计：两段式确认防幻觉金额

加分叙事（你的独特背景）：你懂增长——可以把"注册→入金→购买链路长导致流失"的业务判断映射到产品设计上："记账→分类→复盘→决策"也是链路，本项目每一层都在压缩链路、降低摩擦。面试官会记住"这个人既懂业务漏斗，又能把 AI 工程落地"。

三个关键选型决策（面试必讲）

为什么自建后端

wx.cloud.extend.AI / CloudBase Agent 确实能省掉后端——但面试官想听的是你如何设计系统，而不是你如何配置平台。自建 = 每个技术点都可控可讲：Prompt、RAG、降级、成本，全是你的。

为什么 pgvector 一套库

账单既要做 SQL 聚合（"上月餐饮花多少"）又要做语义检索（"那家日料店"）。用一套 PostgreSQL 同时承载结构化数据 + 向量，省掉向量库的运维和一致性同步问题——这是混合检索架构的地基。

为什么原生小程序

面试展示的是"AI 应用工程师"能力，不是"前端框架熟练度"。原生 TS + 组件化足够；且微信同声传译、ECharts 等官方/成熟生态都是原生友好。少一个构建层，多一份可控。

关键设计：两段式"解析 → 确认"流

所有 AI 入口（语音/拍照/手输）都走同一条链路：先产出"结构化草稿"给用户看，用户确认后才入库。原因：LLM 会幻觉金额，OCR 会认错字——让 AI 承担"加速输入"而非"替你做主"，这是产品信任的关键，也是面试官爱听的工程判断。

链路：入口（语音/拍照/手输）→ /parse 或 /ocr 产出草稿 → 前端展示草稿（金额/类别/描述/时间，可编辑）→ 用户确认 → POST /bills 入库（此时才调分类）

数据库设计

PostgreSQL + pgvector

四张表总览

表职责核心字段设计要点
users用户openid(uniq) / nickname / avataropenid 即身份，不存密码
bills账单明细user_id / amount / category / sub_category / description / source / raw_text / bill_timecategory 固定枚举；source 记录入口（manual/voice/ocr）
bill_vectors账单向量bill_id(FK) / embedding vector(1024)与 bills 分表：主表瘦身、向量可独立重建
monthly_reports月报缓存user_id / month / content jsonb洞察结果落库，避免重复调用 LLM

分类枚举（内置，固定）

餐饮、交通、购物、居住、娱乐、医疗、教育、人情、旅行、投资、转账、其他 —— 12 类。子类不建表，由 LLM 在枚举内自由产出（如"餐饮 → 咖啡"）。固定大类是后续聚合统计和 SQL 检索的基石。

建表 SQL（核心）

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE users (
  id          BIGSERIAL PRIMARY KEY,
  openid      TEXT NOT NULL UNIQUE,
  nickname    TEXT,
  avatar      TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE bills (
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id),
  amount      NUMERIC(12,2) NOT NULL CHECK (amount > 0),
  category    TEXT NOT NULL,
  sub_category TEXT,
  description TEXT,
  source      TEXT NOT NULL DEFAULT 'manual',  -- manual | voice | ocr
  raw_text    TEXT,                                -- AI 解析前的原文，可追溯
  bill_time   TIMESTAMPTZ NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_bills_user_time ON bills(user_id, bill_time DESC);
CREATE INDEX idx_bills_user_cat  ON bills(user_id, category, bill_time DESC);

CREATE TABLE bill_vectors (
  bill_id     BIGINT PRIMARY KEY REFERENCES bills(id) ON DELETE CASCADE,
  embedding   vector(1024) NOT NULL,       -- BGE-M3 维度
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_bill_vectors_hnsw ON bill_vectors
  USING hnsw (embedding vector_cosine_ops);

CREATE TABLE monthly_reports (
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id),
  month       TEXT NOT NULL,               -- '2026-09'
  content     JSONB NOT NULL,              -- 聚合数据 + AI 洞察文本
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE(user_id, month)
);

面试讲点：为什么 bills 与 bill_vectors 分表？① 主表避免携带 1024 维向量的大字段，扫描更轻；② 向量可随时全量重建（改 embedding 模型不碰主表）；③ 通过 ON DELETE CASCADE 保证一致性。分表理由能讲出数据库设计思考。

关键接口示例：语音解析（parse）

# POST /api/v1/bills/parse
# 请求
{ "text": "中午和同事吃了顿火锅 87 块" }

# 响应：结构化草稿（前端展示给用户确认）
{
  "amount": 87.00,
  "category": "餐饮",
  "sub_category": "火锅",
  "description": "中午和同事吃火锅",
  "bill_time": "2026-09-21T13:30:00+08:00",
  "confidence": 0.92,
  "warnings": []
}

关键接口示例：账单问答（chat）

# POST /api/v1/chat
{ "question": "上个月我奶茶一共花了多少？" }

# 响应
{
  "answer": "8 月你共有 14 笔奶茶类消费，合计 186.50 元，占餐饮总支出的 12%。单笔最高 22 元（8-16 某茶），建议关注下午茶频次。",
  "sources": [{ "type": "sql", "hits": 14 }],
  "caveat": "基于 8 月 1 日–31 日账单"
}

接口设计要点：① parse/ocr 与 create 分离——AI 只产出草稿，入库在用户确认后，防幻觉金额；② 分类在创建时同步调用便宜模型（延迟可接受，失败走规则兜底）；③ 所有响应带 caveat/confidence，AI 结论可追溯，这是工程严谨性的直接体现。

核心 AI 设计

4 套 Prompt · 防幻觉 · 混合检索 · 降级

8.1 分类引擎（最高频调用，成本敏感）

设计目标：便宜、快、稳定。用 DeepSeek 便宜档模型 + 固定枚举约束 + JSON 输出 + 规则兜底。

# system：
你是账单分类助手。将消费描述归入以下类别之一：
餐饮/交通/购物/居住/娱乐/医疗/教育/人情/旅行/投资/转账/其他。
只输出 JSON：{"category": "餐饮", "sub_category": "咖啡", "confidence": 0.95}

# few-shot：
用户：瑞幸拿铁大杯 19.9    → {"category":"餐饮","sub_category":"咖啡","confidence":0.98}
用户：滴滴快车 12.5        → {"category":"交通","sub_category":"打车","confidence":0.97}
用户：给爸妈转账 5000      → {"category":"人情","sub_category":"赡养","confidence":0.9}

# 后端校验（Pydantic）：
1. 校验 category ∈ 枚举，否则 重试 1 次（提示错误类别）
2. 仍失败 → 规则兜底：关键词表匹配（"咖啡/奶茶/外卖"→餐饮）
3. confidence < 0.6 → 前端标记"待确认"

8.2 语音/文本解析（金额防幻觉是核心）

语音转文字后，LLM 要把一句口语拆成结构化字段。金额是钱，绝对不能幻觉——为此做了三道防线：

  1. 正则优先：先从原文提取所有数字候选（"87"、"87块"），作为候选金额传给 LLM，并要求"必须从候选中选择"。
  2. 交叉校验：LLM 输出的金额若不在候选数字中，拒绝本次解析并重试一次。
  3. 用户确认：草稿页金额高亮展示，用户可一键修改。

8.3 月度洞察（防编造数字）

LLM 生成"洞察结论"时容易编造数据。方案：后端先算好聚合事实，LLM 只负责解读事实，且要求每条洞察必须引用给定数字，后端校验引用一致才落库。

# 喂给 LLM 的聚合事实（后端算好，真实数据）：
{ "month": "2026-08", "total": 4862.5, "top_categories": [
  {"餐饮": 1520.0, "占比": "31%"}, {"居住": 1200.0, "占比": "25%"} ],
  "mom_change": { "餐饮": "+18%", "total": "+6%" },
  "anomalies": ["订阅类支出连续 3 个月上涨"] }

# 要求：
输出 3-5 条洞察，每条必须引用上述数字，格式：
{"insight": "…", "evidence": "餐饮支出 1520 元，占 31%，环比 +18%"}
# 后端校验：evidence 中的数字必须与聚合事实一致，不一致则丢弃该条

8.4 账单问答：混合检索（全项目最亮的技术点）

账单是"结构化 + 文本"混合数据。纯 RAG 回答不了"奶茶一共花多少"（需要聚合）；纯 SQL 回答不了"上次那家特别好吃的日料店"（需要语义）。所以两路并行：

chat 服务 · 混合检索流程（示意）

高频追问 FAQ（先自己想一遍答案）

为什么自建后端，不用微信云开发的 AI 全家桶？

云开发能更快跑通，但它把模型调用、Agent、向量检索都封装成了配置项——面试要展示的是系统设计能力，自建让我能把 Prompt 工程、降级链、成本控制每一个决策讲清楚。平台能力我用了该用的部分（语音、OCR 免费通道），技术含金量部分留给自己。

分类准确率怎么保证？如果 LLM 乱分类怎么办？

三层：固定枚举约束 + few-shot 示例约束输出空间；Pydantic 校验类别合法性，非法则带错误提示重试一次；仍失败走关键词规则兜底。另外置信度低于阈值的结果前端标"待确认"，把最终决定权留给用户——准确率不可能 100%，设计上允许纠错。

为什么账单问答用混合检索，而不是纯 RAG？

账单是结构化 + 文本混合数据。聚合类问题（"奶茶花了多少"）需要 SQL 按类别求和，纯向量检索答不了；回忆类问题（"那家日料店叫啥"）关键词拼不准，纯 SQL 答不了。所以 LLM 先路由意图，聚合问题走函数调用转 SQL，语义问题走向量召回，复杂问题两路证据合并，最后统一生成带来源的回答。

向量库为什么选 pgvector，不用专门向量数据库？

项目规模下，专门向量库是多余的服务和运维成本，还引入与主库的一致性同步问题。pgvector 让结构化数据和向量同库、同事务，账单增删改时向量通过级联保持一致，一套 PostgreSQL 解决。等数据量到百万级再评估迁专门向量库。

怎么防止 LLM 编造金额和报告数字？

三类手段：金额——正则先从原文提取数字候选，要求 LLM 必须从候选中选，输出不在候选内就拒绝重试，再加上用户确认；报告——后端先算聚合事实，LLM 只能引用给定数字，后端校验引用一致性，不一致丢弃；问答——回答必须带 sources 和 caveat，可追溯。

成本怎么控制的？

分类是最高频调用，用便宜模型 + 相同描述缓存分类结果；月报结果落库，同月不重复生成；输入截断控制 token；OCR 和语音走免费额度。演示规模一个月不到几块钱。

用户量大了怎么扩展？

当前架构的水平扩展路径：FastAPI 无状态可横向扩容 + 负载均衡；分类缓存升级为 Redis；月报生成改为异步任务队列；pgvector 到瓶颈后，向量检索拆到专用向量库或只读从库。这些都是标准演进路线，我在代码里留了接口抽象。

账单是敏感数据，安全合规怎么考虑？

openid 即身份、JWT 鉴权、所有查询强制按 user_id 隔离；不落明文敏感信息；提供数据导出和注销即删；小程序隐私协议里明确数据用途。个人信息保护法对财务数据的处理要求是面试官可能追问的点。
